# 4. Commit-SHA image tags and a pinned supply chain

**Status:** accepted

## Context
A tag like `latest` can point to different images over time, so "what's running?" has no exact answer. The same goes for CI tooling and base images: in March 2026, attackers re-pointed most of Trivy's GitHub Action version tags to credential-stealing code.

## Decision
- Images are tagged with the **full git commit SHA**. The running version is exposed in every API response and in metrics (`version` label).
- GitHub Actions are pinned to **commit SHAs**. Trivy and Prometheus (for `promtool`) run as container images pinned by **digest**. kubeconform is downloaded with a **checksum check**, and its CRD schemas come from a **pinned commit** of the schema catalog.
- Base images (`python:3.14-slim`, `busybox:1.37`) are pinned by **multi-arch index digest**.
- Python dependencies are **fully locked**: `requirements.in` holds the top-level pins, and `requirements.txt` is the complete lock generated by `pip-compile` inside the runtime image.
- The Trivy scan **fails the build** on fixable CRITICAL vulnerabilities, and nothing is pushed.
- pip is removed from the runtime image (Trivy found 4 HIGH CVEs in pip's bundled libraries; after removal, 0).
- Dependabot opens PRs to move pins forward deliberately.

## What this does *not* guarantee
- SHA tags are **unique per commit, not immutable**. GHCR lets anyone with push rights overwrite a tag, so `gitops-api:<sha>` could in theory be re-pushed with different contents. The next step is to **deploy by digest** (`image@sha256:...`) in `apps/<env>/*.yaml`, so the cluster runs exactly the bytes CI scanned.
- The Python lock has no hashes, so it pins versions, not file contents.

## Consequences
- Every pod traces back to an exact commit, and a `git revert` points the cluster back at the previous commit's image.
- A re-pointed upstream tag (action, base image, scanner) can't silently change what CI builds or runs.
- Cost: pins must be bumped. Dependabot automates the PRs.
